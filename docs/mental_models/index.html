📖 How to use this information

This is a decision-support tool, not a checklist. Use it to build architectural intuition.

For architects starting a new mission-critical project

  1. Start with the foundational models (🧠 gold cards) — these are ways of thinking, not specific technologies. Internalize "Blast Radius", "Assume Failure", and "Simplicity" before choosing any Azure service.
  2. Use the structural models (🏗️ blue cards) to shape your architecture — Scale Units, Health Modeling, Active/Active. These determine your deployment topology.
  3. Apply operational models (⚙️ green cards) to decide how you'll run it — Automation, Observability, Chaos Engineering, Error Budgets.
  4. Check anti-patterns — scan the ⚠️ section below to verify you're not drifting toward known failure modes.

For teams reviewing an existing workload

  1. Pick 3-5 model cards most relevant to your current pain points
  2. Read the "Without it" section — if you recognize your system, that model needs attention
  3. Check the "Builds on" links — you might be missing a prerequisite mental model
  4. Explore the knowledge graph to trace connections between concepts

For learning and onboarding

Mental models are listed in dependency order. The top cards are foundational — everything else builds on them. Reading order:

  1. Blast Radius → Simplicity → Assume Failure (foundations)
  2. Scale Units → Health Modeling → Active/Active (structure)
  3. Automation → Observability → Error Budgets (operations)
  4. Zero Trust → Defense in Depth (security)

Each card's "Key tradeoff" tells you what you're giving up — there are no free lunches in reliability engineering.

Understanding the data

Centrality = how many connections a concept has in the knowledge graph. High centrality = the concept touches many other areas.

Bridge score = how much a concept connects otherwise-disconnected parts of the graph. High bridge = removing this concept would fragment understanding.

Layer = where the model sits in the thinking hierarchy. You must internalize lower layers before upper layers are useful.

Zero Trust

"Never trust, always verify every request."

🎯 When to apply

  • Designing network access policies for cloud workloads
  • Handling sensitive or mission-critical workloads
  • Assuming breach and hardening internal traffic
  • Implementing identity-based access controls
  • Segmenting workloads to limit blast radius

💥 Without it

  • Lateral movement by attackers after initial breach
  • Over-trusted internal network traffic
  • Undetected compromised identities accessing resources
  • Flat network architectures with no segmentation
  • Delayed breach detection and response

⚖️ Key tradeoff

Stronger security verification increases operational complexity and may impact latency and user experience.

🔗 Builds on: Defense-In-Depth, Micro-Segmentation, Network Security Groups, Security Readiness Plan
🔗 Enables: Microsoft Zero Trust Model, Mission-Critical Workloads, Micro-Segmentation

Reliability Design Principles

"Design every workload to survive failure and keep serving its purpose."

🎯 When to apply

  • Starting architecture design for a new workload
  • Reviewing existing systems for reliability gaps
  • Defining SLAs and recovery targets with stakeholders
  • Making tradeoff decisions between cost and resilience

💥 Without it

  • Cascading failures from unplanned outages
  • No clear recovery strategy when things break
  • Misaligned reliability targets with business needs
  • Reactive firefighting instead of proactive design
  • Inconsistent resilience patterns across services

⚖️ Key tradeoff

Higher reliability demands more redundancy and complexity, increasing cost and operational overhead.

🔗 Builds on: Design For Business Requirements
🔗 Enables: Availability, Design For Resilience, Recoverability, Resilience, Reliability Checklist
🔒 security 6 connections

Assume Breach

"Design every defense as if the attacker is already inside."

🎯 When to apply

  • Designing network segmentation and containment strategies
  • Planning encryption for data at rest and in transit
  • Building incident response and disaster recovery plans
  • Evaluating compensating controls for critical systems
  • Implementing Zero Trust architectures

💥 Without it

  • Over-reliance on perimeter defenses with no internal controls
  • Unencrypted sensitive data exposed after a breach
  • No containment strategy allowing lateral movement
  • Delayed detection due to missing audit trails
  • Catastrophic data exfiltration from a single compromised account

⚖️ Key tradeoff

Increased operational complexity and cost of layered defenses versus the risk of unchecked damage from an undetected compromise.

🔗 Builds on: Microsoft Zero Trust Model, Encryption, Audit Trail
🔗 Enables: Confidentiality, Data Exfiltration, Disaster Recovery
📊 data 5 connections

Four Vs Of Big Data

"Characterize your data by Volume, Velocity, Variety, and Veracity before designing anything."

🎯 When to apply

  • Designing a new big data platform on Azure
  • Evaluating storage and compute requirements for data workloads
  • Assessing data quality and trustworthiness needs
  • Choosing between batch and real-time processing architectures

💥 Without it

  • Under-provisioned storage that cannot handle data volume growth
  • Pipelines that fail under real-time ingestion demands
  • Brittle schemas that break when diverse data formats arrive
  • Decisions made on untrustworthy or unvalidated data

⚖️ Key tradeoff

Optimizing for one V (e.g., velocity) often increases cost or complexity in another (e.g., veracity).

🔗 Builds on: Azure
🔗 Enables: Volume, Velocity, Variety, Veracity
⚙️ operational 5 connections

Design For Recovery

"Assume failure will happen and make bouncing back automatic."

🎯 When to apply

  • Architecting new workloads that require high availability
  • Defining RTO and RPO targets for critical systems
  • Preparing for regional or zonal outages
  • Introducing stateful components that risk data loss
  • Reviewing resilience posture after an incident

💥 Without it

  • Extended downtime with no clear path to restoration
  • Permanent data loss from unrecoverable failures
  • Cascading failures spreading across dependent services
  • Panic-driven manual recovery increasing human error
  • Violated SLAs and eroded customer trust

⚖️ Key tradeoff

Investing in recovery mechanisms increases complexity and cost versus accepting higher risk of prolonged outages.

🔗 Builds on: Backups, Disaster Preparedness, Recovery Plans
🔗 Enables: Self-Healing, Immutable Ephemeral Units
🔒 security 5 connections

Least Privilege

"Grant only what's needed, only when it's needed, and not a bit more."

🎯 When to apply

  • Assigning permissions to users or service accounts
  • Configuring access to production environments
  • Designing API authorization scopes
  • Onboarding new team members or workloads
  • Reviewing existing access policies for drift

💥 Without it

  • Lateral movement by attackers through over-privileged accounts
  • Accidental data deletion or corruption by users with excessive rights
  • Compliance violations from broad standing access
  • Blast radius of compromised credentials expands dramatically
  • Audit trails become meaningless when everyone has admin access

⚖️ Key tradeoff

Tighter access controls increase operational friction and complexity versus reducing security risk and blast radius.

🔗 Builds on: Access Controls, Just-Enough-Access, Just-In-Time Access
🔗 Enables: Integrity, Availability

Zero-Downtime Deployment

"Ship fearlessly without ever turning off the lights."

🎯 When to apply

  • Releasing new versions of mission-critical applications
  • Applying infrastructure changes to production scale units
  • Rolling out hotfixes under active user traffic
  • Migrating between platform versions in-place

💥 Without it

  • Planned maintenance windows that erode availability SLAs
  • Failed deployments causing full service outages
  • Customer-visible errors during release rollouts
  • Fear of deploying leads to infrequent, risky big-bang releases

⚖️ Key tradeoff

Achieving zero downtime demands additional infrastructure complexity and cost (blue-green or canary patterns, scale-unit isolation) in exchange for uninterrupted availability.

🔗 Builds on: Scale-Unit Architecture, Azure
🔗 Enables: Azure Mission-Critical Connected, Mission-Critical Online

🎯 When to apply

  • Architecting new cloud workloads with uptime requirements
  • Identifying and hardening critical path components
  • Preparing systems for partial infrastructure failures
  • Reviewing reliability posture during design reviews

💥 Without it

  • Total outage from a single component failure
  • No fallback behavior when dependencies are unavailable
  • Cascading failures across tightly coupled services
  • Users experience hard errors instead of reduced functionality

⚖️ Key tradeoff

Increased architectural complexity and cost versus the ability to maintain service continuity during failures.

🔗 Builds on: Critical Path, Reliability Design Principles
🔗 Enables: Fault Tolerance, Graceful Degradation

Verify Explicitly

"Never trust, always validate every identity, action, and location."

🎯 When to apply

  • Authenticating users or services accessing resources
  • Processing data modification requests
  • Evaluating access from unexpected locations or devices
  • Designing API authorization flows
  • Implementing cross-service communication

💥 Without it

  • Implicit trust allows lateral movement by attackers
  • Unauthorized data modifications go undetected
  • Compromised credentials grant unchecked access
  • Insider threats exploit overly permissive defaults
  • Compliance violations from unverified access

⚖️ Key tradeoff

Stronger explicit verification increases security but adds latency and friction to user and system interactions.

🔗 Builds on: Microsoft Zero Trust Model, Data Classification
🔗 Enables: Integrity, Availability
🔒 security 4 connections

Microsoft Zero Trust Model

"Never trust, always verify — treat every request as if it originates from a hostile network."

🎯 When to apply

  • Designing identity and access controls for a new workload
  • Evaluating network segmentation and micro-perimeter strategies
  • Responding to an evolving threat landscape or compliance mandate
  • Migrating on-premises workloads to the cloud
  • Reviewing existing security posture for implicit trust assumptions

💥 Without it

  • Implicit trust allows lateral movement after a single breach
  • Over-privileged identities amplify blast radius of compromised accounts
  • Unverified requests slip through perimeter-only defenses
  • Security gaps go undetected until a major incident occurs
  • Compliance failures due to lack of granular access controls

⚖️ Key tradeoff

Stronger security verification at every layer increases operational complexity and can add latency to user and service interactions.

🔗 Builds on: Zero Trust
🔗 Enables: Assume Breach, Least-Privilege Access, Verify Explicitly

Cost-Efficiency Mindset

"Spend only on what earns its keep."

🎯 When to apply

  • Starting a new cloud workload or migration
  • Reviewing monthly Azure spend reports
  • Provisioning SDLC and non-production environments
  • Evaluating architecture trade-offs between performance and cost

💥 Without it

  • Unchecked resource sprawl and zombie resources
  • Over-provisioned non-production environments mirroring production
  • No accountability for cloud spend across teams
  • Reactive cost firefighting instead of proactive planning

⚖️ Key tradeoff

Minimizing spend while still investing enough to meet reliability, performance, and security requirements.

🔗 Builds on: Cost Baseline
🔗 Enables: Cost Guardrails, Cost Optimization, SDLC Environments
⚙️ operational 4 connections

Design For Rate Optimization

"Squeeze more value from every dollar already committed."

🎯 When to apply

  • Reviewing existing resource spend for waste
  • Choosing between consumption-based and fixed-price models
  • Negotiating enterprise agreements or reservations
  • Leveraging hybrid use benefits for licensed software
  • Right-sizing resources without changing architecture

💥 Without it

  • Overpaying for underutilized reserved capacity
  • Missing available licensing discounts like hybrid use
  • Defaulting to pay-as-you-go when commitments save more
  • Costs growing linearly while utilization stays flat

⚖️ Key tradeoff

Commitment depth versus flexibility—locking in lower rates reduces agility to change.

🔗 Builds on: Consumption-Based Pricing, Fixed-Price Billing, Hybrid Use
🔗 Enables: Consumption-Based Pricing, Fixed-Price Billing

Defense-In-Depth

"Never rely on a single layer of security—stack your defenses."

🎯 When to apply

  • Designing network segmentation and boundary controls
  • Implementing compensating controls after threat modeling
  • Protecting critical assets with multiple authentication barriers
  • Hardening workloads across identity, network, and data layers

💥 Without it

  • Single point of compromise leads to full breach
  • Lateral movement goes undetected across flat networks
  • One misconfiguration exposes entire system
  • Threat actors bypass the only security control in place

⚖️ Key tradeoff

More security layers increase complexity and operational cost versus the risk reduction they provide.

🔗 Builds on: Threat Modeling, Zero Trust
🔗 Enables: SE:06
🏗️ structural 3 connections

Blast Radius

"Contain every failure before it contains you."

🎯 When to apply

  • Designing isolation boundaries between components
  • Planning multi-tenant resource co-location
  • Evaluating deployment stamp or cell-based architectures
  • Conducting failure mode analysis on critical flows
  • Assessing security compromise impact scope

💥 Without it

  • Single fault cascades across the entire system
  • Tenant noisy-neighbor problems cause widespread outages
  • Security breaches escalate to full environment compromise
  • Deployments gone wrong take down all users simultaneously

⚖️ Key tradeoff

Smaller blast radius requires more isolation boundaries, increasing cost and operational complexity.

🔗 Builds on: Failure Mode Analysis, Self-Preservation
🔗 Enables: Multitenancy
⚙️ operational 3 connections

Automation

"Automate everything you'd regret doing manually twice."

🎯 When to apply

  • Deploying infrastructure or application changes
  • Running repetitive operational tasks
  • Scaling workloads to meet demand
  • Executing test suites across environments
  • Responding to monitoring alerts with remediation

💥 Without it

  • Human errors in deployments cause outages
  • Inconsistent environments lead to drift and bugs
  • Slow response to incidents due to manual intervention
  • Accumulating technical debt from unscripted processes
  • Operations that don't scale with workload growth

⚖️ Key tradeoff

Upfront investment in building and maintaining automation versus the ongoing cost and risk of manual processes.

🔗 Builds on: Monitoring System
🔗 Enables: Reliability, Well-Architected Framework

Cost-Management Discipline

"Make every dollar visible, owned, and intentional."

🎯 When to apply

  • Standing up a new cloud workload or environment
  • Monthly or quarterly budget review cycles
  • When cloud spend is growing faster than business value
  • Onboarding new teams to shared infrastructure

💥 Without it

  • Uncontrolled cloud sprawl and bill shock
  • No ownership of costs leads to finger-pointing
  • Inability to forecast or plan capacity spending
  • Optimization efforts are reactive instead of proactive

⚖️ Key tradeoff

Rigorous cost tracking adds process overhead that can slow teams down, but without it spending becomes invisible and unaccountable.

🔗 Builds on: Accountability Model
🔗 Enables: Cost Optimization, Service-Level Agreements

Design For Usage Optimization

"Squeeze every drop of value from every resource you provision."

🎯 When to apply

  • Workload costs are growing faster than business value
  • Resources sit idle during off-peak periods
  • Deploying across multiple regions for availability
  • Evaluating commitment-based pricing models
  • Right-sizing compute and storage resources

💥 Without it

  • Chronic overprovisioning and wasted spend
  • Idle resources consuming budget with no return
  • Missed discount opportunities from cloud providers
  • Inability to meet nonfunctional requirements cost-effectively
  • Scaling decisions driven by guesswork rather than demand

⚖️ Key tradeoff

Maximizing utilization increases efficiency but risks insufficient headroom for unexpected demand spikes.

🔗 Builds on: Dynamic Scaling, Active-Active Model
🔗 Enables: Commitment-Based Discounts, Dynamic Scaling, Active-Active Model
📊 data 2 connections

CAP Theorem

"Pick two: consistency, availability, or partition tolerance—you cannot have all three."

🎯 When to apply

  • Designing distributed databases with multiple replicas
  • Choosing between strong and eventual consistency models
  • Architecting globally distributed applications
  • Evaluating database technologies for resilience requirements

💥 Without it

  • Assuming a distributed system can be both perfectly consistent and always available
  • Unexpected data staleness surprising end users
  • System outages during network partitions due to rigid consistency demands
  • Poor latency from enforcing unnecessary consistency guarantees

⚖️ Key tradeoff

Stronger consistency guarantees come at the cost of availability and latency, especially during network partitions.

🔗 Builds on: Veracity
🔗 Enables: PACELC Theorem
🏗️ structural 2 connections

Self-Preservation

"Design every component to protect itself so failures stay local."

🎯 When to apply

  • Designing modular service boundaries
  • Implementing retry, circuit-breaker, or bulkhead patterns
  • Evaluating cascading failure risks
  • Adding health checks and graceful degradation paths

💥 Without it

  • Single component failure cascades across the entire system
  • Downstream services overwhelmed by upstream failures
  • Uncontrolled blast radius during incidents
  • Extended outages due to lack of graceful degradation

⚖️ Key tradeoff

Stronger self-preservation increases component complexity and latency overhead versus broader system resilience.

🔗 Builds on: Blast Radius
🔗 Enables: RE:07
⚙️ operational 2 connections

Design For Operations

"Anticipate failure before your customers discover it."

🎯 When to apply

  • Designing new services or features for production readiness
  • Planning testing strategies for complex distributed systems
  • Establishing observability and monitoring requirements
  • Conducting failure mode analysis during architecture reviews

💥 Without it

  • Failures surface first through customer complaints
  • Debugging production issues becomes guesswork without telemetry
  • Mean time to recovery balloons due to poor operational tooling
  • Recurring incidents with no systematic root cause resolution

⚖️ Key tradeoff

Investing in operational readiness upfront increases development cost but dramatically reduces incident impact and recovery time.

🔗 Builds on: Observable Systems, Root Cause Analysis
🔗 Enables: Observable Systems, Root Cause Analysis
