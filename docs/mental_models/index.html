📖 How to use this information

This is a decision-support tool, not a checklist. Use it to build architectural intuition.

For architects starting a new mission-critical project

  1. Start with the foundational models (🧠 gold cards) — these are ways of thinking, not specific technologies. Internalize "Blast Radius", "Assume Failure", and "Simplicity" before choosing any Azure service.
  2. Use the structural models (🏗️ blue cards) to shape your architecture — Scale Units, Health Modeling, Active/Active. These determine your deployment topology.
  3. Apply operational models (⚙️ green cards) to decide how you'll run it — Automation, Observability, Chaos Engineering, Error Budgets.
  4. Check anti-patterns — scan the ⚠️ section below to verify you're not drifting toward known failure modes.

For teams reviewing an existing workload

  1. Pick 3-5 model cards most relevant to your current pain points
  2. Read the "Without it" section — if you recognize your system, that model needs attention
  3. Check the "Builds on" links — you might be missing a prerequisite mental model
  4. Explore the knowledge graph to trace connections between concepts

For learning and onboarding

Mental models are listed in dependency order. The top cards are foundational — everything else builds on them. Reading order:

  1. Blast Radius → Simplicity → Assume Failure (foundations)
  2. Scale Units → Health Modeling → Active/Active (structure)
  3. Automation → Observability → Error Budgets (operations)
  4. Zero Trust → Defense in Depth (security)

Each card's "Key tradeoff" tells you what you're giving up — there are no free lunches in reliability engineering.

Understanding the data

Centrality = how many connections a concept has in the knowledge graph. High centrality = the concept touches many other areas.

Bridge score = how much a concept connects otherwise-disconnected parts of the graph. High bridge = removing this concept would fragment understanding.

Layer = where the model sits in the thinking hierarchy. You must internalize lower layers before upper layers are useful.

Zero Trust

"Never trust, always verify every request."

🎯 When to apply

  • Designing network access policies for cloud workloads
  • Protecting mission-critical workloads from lateral movement
  • Implementing identity-based access across application layers
  • Responding to an assumed-breach security posture
  • Segmenting workloads in multi-tenant environments

💥 Without it

  • Lateral movement after a single breach compromises entire network
  • Implicit trust allows unauthorized access between services
  • Overly permissive network policies go undetected
  • Insider threats exploit flat network topologies
  • Compliance failures due to lack of access verification

⚖️ Key tradeoff

Stronger security verification increases complexity and may add latency versus the risk of implicit trust.

🔗 Builds on: Defense-In-Depth, Micro-Segmentation, Network Security Groups, Security Readiness Plan
🔗 Enables: Microsoft Zero Trust Model, Mission-Critical Workloads, Micro-Segmentation

CAP Theorem

"Pick two: consistency, availability, or partition tolerance—you cannot have all three."

🎯 When to apply

  • Designing distributed databases with multiple replicas
  • Choosing between strong and eventual consistency models
  • Architecting globally distributed applications
  • Evaluating database technologies for resilience requirements

💥 Without it

  • Assuming a distributed system can be perfectly consistent and always available
  • Unexpected data staleness surprising users and downstream systems
  • Over-engineering for consistency at the cost of availability
  • Choosing databases that don't match actual workload trade-off needs

⚖️ Key tradeoff

Consistency versus availability during network partitions, forcing architects to prioritize one over the other.

PACELC Theorem

"Even when things are fine, you're still trading latency for consistency."

🎯 When to apply

  • Choosing between eventual and strong consistency for a distributed database
  • Evaluating latency-sensitive workloads that also need partition tolerance
  • Designing replication strategies across regions
  • Comparing managed database offerings and their consistency models

💥 Without it

  • Assuming CAP fully describes your system's behavior during normal operation
  • Unexpected latency spikes from strong consistency you didn't need
  • Stale reads in systems where you assumed consistency came for free
  • Poor user experience from ignoring the latency-consistency spectrum

⚖️ Key tradeoff

During normal operation (no partition), you must still choose between lower latency and stronger consistency.
